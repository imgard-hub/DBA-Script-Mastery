Module 1 · 75 min

Foundations of DBA Scripting

Learning Objectives

  • Explain what a “DBA script” is and why almost all DBA work is script-driven.
  • Navigate the Oracle data dictionary (ALL_/DBA_/USER_ views, V$ views).
  • Understand SQL*Plus vs. SQLcl and when to use each.
  • Apply basic script safety practices before running anything against production.

Lesson

A “DBA script” is just a saved, reusable question you ask the database — written once, run many times, sometimes with a parameter swapped in. Almost everything a DBA does day-to-day, from checking tablespace space to building a full constraints report, is a script someone wrote once and kept. This module starts from the real scenario that motivates this whole course: your manager asks you to pull every primary key, foreign key, and constraint for a schema, and hand back something readable. With only basic SELECT knowledge, that request is genuinely hard to know where to start — this module gives you the map.

The data dictionary: three families of views

Oracle keeps metadata about every object — tables, columns, constraints, indexes — in its data dictionary. You will mostly work with three families of views, which differ only in whose objects they show you:

View prefixShows youNeeds
USER_*Objects you ownNothing extra — always available
ALL_*Objects you own or have been granted privileges onA grant on the object
DBA_*Every object in the database, regardless of ownerDBA-level privilege (e.g. SELECT_CATALOG_ROLE)

A common beginner mistake is querying USER_TABLES and being confused when another schema’s tables don’t show up — that view only ever shows the connected user’s own objects. If you’re building a script to inspect a schema you don’t own, you need ALL_* or DBA_*.

The four-view join path

Constraint reporting always follows the same connected path through the dictionary. Memorize this shape — you will reuse it constantly:

ALL_TABLES
   → ALL_TAB_COLUMNS      (every column of every table)
   → ALL_CONSTRAINTS      (every constraint: P=primary key, R=foreign key, U=unique, C=check)
   → ALL_CONS_COLUMNS     (which column(s) belong to each constraint)

Foreign keys need one extra step: ALL_CONSTRAINTS is joined to itself, matching a row’s R_CONSTRAINT_NAME to the primary/unique constraint it references, in order to resolve which table and column a foreign key actually points to. You’ll build this self-join by hand in Module 3.

SQL*Plus vs. SQLcl

SQL*Plus is the original, universally-available command-line client — every Oracle install has it, and almost every legacy DBA script in the wild is written for it. SQLcl (SQL Developer Command Line) is Oracle’s newer client: it understands the same SET/ACCEPT/SPOOL commands, adds things like built-in JSON and liquibase support, command history, and better tab completion. For this course, scripts are written to run in either — but when you see a script that behaves oddly in one client and not the other, that’s usually the first thing to suspect.

Formatting isn’t cosmetic

Before you run almost any script, these SET commands change whether the output is usable at all:

SET LINESIZE 200      -- characters per line before wrapping
SET PAGESIZE 50000    -- rows before repeating column headers
SET FEEDBACK OFF      -- suppress "N rows selected"
SET HEADING ON        -- keep column headers (or OFF for clean CSV)

Skip LINESIZE/PAGESIZE and a perfectly correct query can look wrapped and broken — new DBAs often assume the query is wrong when it’s actually just the formatting.

Script safety, before you run anything

  • Know which environment you’re connected to — run SELECT name FROM v$database; or check your prompt.
  • Know which schema you’re connected as — SHOW USER or SELECT USER FROM DUAL;.
  • Know what a script’s SPOOL will overwrite — check the filename before you run it a second time.
  • Never run an unfamiliar script against production first — read it, then test it in a sandbox.

Module 2 · 90 min

Building Simple Scripts

Learning Objectives

  • Write single-purpose, parameterized SELECT scripts using ACCEPT and substitution variables.
  • Use NEW_VALUE to generate dynamic filenames for SPOOL output.
  • Format output for readability with COLUMN, and export to CSV with SET MARKUP CSV.
  • Know the difference between a “quick lookup” script and a “report” script.

Lesson

Once you can read the dictionary, the next skill is turning a one-off query into a reusable tool: something that asks you for input, writes its output to a sensibly-named file, and can be handed to someone else to run without editing the script itself.

ACCEPT and substitution variables

ACCEPT prompts the person running the script for a value and stores it in a substitution variable, referenced with &:

ACCEPT p_schema CHAR PROMPT 'Enter schema owner: '

SELECT table_name FROM all_tables
WHERE owner = UPPER('&p_schema')
ORDER BY table_name;

Two details trip people up constantly. First, dictionary values are stored in uppercase, so always wrap substitution variables in UPPER() — otherwise myschema won’t match MYSCHEMA. Second, a single &var re-prompts every time it’s referenced unless you either use ACCEPT first (as above) or double it as &&var, which prompts once and reuses the value for the rest of the script.

Dynamic filenames with NEW_VALUE

To generate a spool filename that includes the schema name and a timestamp, without hardcoding it, use a throwaway SELECT whose column feeds a substitution variable via NEW_VALUE:

COLUMN output_file NEW_VALUE output_file NOPRINT
SELECT 'report_' || LOWER('&p_schema') || '_' ||
       TO_CHAR(SYSDATE,'YYYYMMDD_HH24MISS') || '.csv' AS output_file
FROM dual;

SPOOL &output_file
... your report query ...
SPOOL OFF

This pattern — a dummy query that only exists to compute a filename — shows up in nearly every report-style script in the library. NOPRINT keeps the dummy query itself from appearing in the output.

Clean CSV export

To spool a genuinely clean CSV (one that opens correctly in Excel with no stray SQL*Plus text), you need all of the following together:

SET FEEDBACK OFF
SET VERIFY OFF
SET TRIMSPOOL ON
SET MARKUP CSV ON QUOTE ON
SPOOL output.csv
SELECT ... FROM ...;
SPOOL OFF
SET MARKUP CSV OFF

Forgetting FEEDBACK OFF or VERIFY OFF leaves system lines like old 3: WHERE owner = '&p_schema' written directly into your CSV, which then breaks any downstream import. export_schema_column_metadata_csv.sql (this course’s anchor script for this module) builds on this exact pattern, adding WITH clauses that flag which columns are part of a primary key or foreign key before the CSV is even generated.

Ad hoc query, or library script?

A simple rule of thumb: if you’ll plausibly be asked this question again — by this client, this manager, or your future self — save it into your library with a proper header comment. If it’s a truly one-time lookup, it’s fine to leave it as scratch work.

Module 3 · 90 min

Building Complex Scripts (PL/SQL Reports)

Learning Objectives

  • Understand when a flat SELECT isn’t enough and a PL/SQL block is needed.
  • Use anonymous PL/SQL blocks with DBMS_OUTPUT to build narrative, human-readable reports.
  • Write and call local functions/procedures inside a DECLARE block.
  • Recognize and fix the LONG-column pitfall (ORA-00932) when working with SEARCH_CONDITION.

Lesson

A flat SELECT can list constraints, but it can’t group them table-by-table with headers, skip cleanly to the next section when a table has no foreign keys, or build in a plain-English “references table X, column Y” line. That’s a job for a PL/SQL block: real code that loops, branches, and prints a narrative report instead of a flat result grid.

Anonymous PL/SQL blocks and DBMS_OUTPUT

An anonymous block has no name and isn’t stored in the database — it runs once and is gone. The skeleton looks like this:

SET SERVEROUTPUT ON SIZE UNLIMITED   -- required, or DBMS_OUTPUT is silently swallowed

DECLARE
  v_count PLS_INTEGER;
BEGIN
  SELECT COUNT(*) INTO v_count FROM all_tables WHERE owner = 'HR';
  DBMS_OUTPUT.PUT_LINE('Table count: ' || v_count);
END;
/                                      -- the trailing slash executes the block

Two mistakes account for most first-time failures here: forgetting SET SERVEROUTPUT ON (the block runs fine, but you never see any output), and forgetting the trailing / (SQL*Plus just sits there, still building the block).

Local functions inside a block

schema_constraints_report.sql, this module’s anchor script, declares a small local function, get_cols, that takes an owner and constraint name and returns a comma-joined list of that constraint’s columns:

FUNCTION get_cols(p_owner VARCHAR2, p_cons_name VARCHAR2) RETURN VARCHAR2 IS
  v_cols VARCHAR2(4000);
BEGIN
  FOR c IN (SELECT column_name FROM all_cons_columns
            WHERE owner = p_owner AND constraint_name = p_cons_name
            ORDER BY position) LOOP
    v_cols := v_cols || c.column_name || ', ';
  END LOOP;
  RETURN RTRIM(v_cols, ', ');
END get_cols;

It’s then called once per constraint inside the main report loop, keeping the reporting logic readable instead of repeating the same cursor everywhere a column list is needed.

Resolving a foreign key’s target: the self-join

This is the trickiest join in the whole course. A foreign key row in ALL_CONSTRAINTS stores which constraint it references — not the table/column directly. To resolve that into a readable “references OWNER.TABLE (COLUMN)” line, you join ALL_CONSTRAINTS to itself:

SELECT c.constraint_name, rc.table_name AS referenced_table
FROM all_constraints c
JOIN all_constraints rc
  ON c.r_owner = rc.owner
 AND c.r_constraint_name = rc.constraint_name
WHERE c.owner = 'HR'
  AND c.constraint_type = 'R';

c is the foreign key itself; rc is the primary/unique constraint it points back to. Once you have rc.table_name, you feed it back into get_cols to print the referenced column(s) too.

Case study: the LONG-column bug

Constraint conditions (SEARCH_CONDITION in ALL_CONSTRAINTS) are stored as a LONG datatype. Oracle only allows a narrow set of operations directly on a LONG column in SQL — and LIKE is not one of them. This script originally tried to filter for NOT NULL checks like this, and it failed:

-- FAILS: ORA-00932: inconsistent datatypes: expected CHAR got LONG
SELECT column_name FROM all_constraints c JOIN all_cons_columns cc ...
WHERE c.search_condition LIKE '%IS NOT NULL%'

The fix: pull the value out with SUBSTR (which Oracle does allow on a LONG, converting it to a bounded VARCHAR2) into a PL/SQL variable, then run the LIKE comparison in PL/SQL instead of in the SQL WHERE clause:

FOR nn IN (
  SELECT cc.column_name, SUBSTR(c.search_condition,1,4000) AS scond
  FROM all_constraints c JOIN all_cons_columns cc ON ...
) LOOP
  IF nn.scond IS NOT NULL AND UPPER(nn.scond) LIKE '%IS NOT NULL%' THEN
    v_cols := v_cols || nn.column_name || ', ';
  END IF;
END LOOP;

This is one of the most common real-world bugs you’ll hit querying the dictionary, and now you’ve already fixed it once.

Module 4 · 60 min

Managing & Maintaining a Script Library

Learning Objectives

  • Organize scripts into a personal library with consistent naming, headers, and categories.
  • Apply basic version-control discipline (even without Git) to avoid overwriting working scripts.
  • Document scripts so another DBA (or future you) can run them without guessing.
  • Know when to retire, merge, or rewrite an old script.

Lesson

A script you can’t find, don’t trust, or don’t understand six months later isn’t really an asset. This module is about the unglamorous habits that make a 50-script library (or a 500-script one) something you can actually rely on.

The header comment convention

Every script in this course’s library opens with the same shape of header, so it’s self-documenting the moment you open the file — no need to run it just to find out what it does:

-- =====================================================================
-- 08. Tablespace Usage Summary
-- Category : Space & Storage Management
-- Purpose  : Show percent used, free, and allocated space per tablespace.
-- Level    : Beginner
-- Usage    : sqlplus user/pass@db @08_tablespace_usage_summary.sql
-- =====================================================================

Four things, every time: what it’s called, what category it belongs to, what it actually does, and how to run it.

Organize by category, not one flat folder

At 10 scripts, a flat folder is fine. At 50, you need categories — this library uses eight: schema/object metadata, space & storage, performance, sessions & locking, users/roles/security, backup/recovery/Data Guard, patching/upgrade/health, and scheduling. At 500 scripts, you may need sub-categories within those. The test is simple: can you find the right script in under a minute without searching by filename alone?

Version discipline, even without Git

The single most common real-world DBA mistake in this area is editing a script that’s mid-use somewhere else — a scheduled job, a colleague’s open session, a runbook step. The minimum viable habit: copy before you edit, and date-stamp the old version (report_v1_2026-08-06.sql) rather than overwriting it. If your team has Git available, a script library is one of the easiest possible places to start using it — git init, git add ., git commit -m "baseline", then commit again every time you meaningfully change a script.

Keep an index

This course ships with script_catalog.md as a model: one row per script, with its path, level, and purpose, grouped by category. As your own library grows past the 50 scripts here, keep adding to your own version of this file — it becomes the fastest way to find something without opening files one by one.

Module 5 · 75 min

Execution & Operations

Learning Objectives

  • Safely execute scripts in non-production and production environments.
  • Read and act on script errors (ORA- codes) rather than guessing.
  • Schedule recurring scripts with DBMS_SCHEDULER.
  • Assemble multiple scripts into a single operational “health check” routine.

Lesson

Everything up to this point has been building and organizing scripts. This module is about running them safely, reading what goes wrong when they don’t work, and combining several into a single deliverable — which is exactly how the motivating scenario for this course actually gets resolved.

The pre-execution checklist

  • Know the environment. SELECT name FROM v$database; — confirm you’re where you think you are.
  • Know the connected user. SHOW USER — especially important with shared/service accounts.
  • Know what the script changes. A SELECT-only script is low-risk; anything with SPOOL, DDL, or DML needs a second look.
  • Have a rollback plan for anything beyond a read-only report.

Reading an error stack

Oracle error stacks read bottom-up, not top-down — the deepest/most specific error is at the bottom, and each line above it is the calling context. Take the exact error from Module 3:

ORA-06550: line 193, column 17:
PL/SQL: ORA-00932: inconsistent datatypes: expected CHAR got LONG
ORA-06550: line 183, column 11:
PL/SQL: SQL Statement ignored
ORA-06550: line 196, column 31:
PLS-00364: loop index variable 'NN' use is invalid

Read from the top down and it looks like three unrelated problems. Read the root cause first (ORA-00932, the LONG/CHAR mismatch) and the rest makes sense: the SQL statement got rejected, so the loop it was feeding never ran, so the loop variable was never valid. Fix the root cause and the rest resolves itself.

Scheduling with DBMS_SCHEDULER

Once a report script works, you can wrap it to run unattended:

BEGIN
  DBMS_SCHEDULER.CREATE_JOB(
    job_name        => 'NIGHTLY_CONSTRAINTS_REPORT',
    job_type        => 'EXECUTABLE',
    job_action      => '/usr/bin/sqlplus',
    number_of_arguments => 1,
    enabled         => FALSE
  );
  DBMS_SCHEDULER.SET_JOB_ARGUMENT_VALUE('NIGHTLY_CONSTRAINTS_REPORT', 1,
    'dba/pw@db @schema_constraints_report.sql');
  DBMS_SCHEDULER.SET_ATTRIBUTE('NIGHTLY_CONSTRAINTS_REPORT','repeat_interval',
    'FREQ=DAILY;BYHOUR=2');
  DBMS_SCHEDULER.ENABLE('NIGHTLY_CONSTRAINTS_REPORT');
END;
/

Always create a scheduler job disabled first, verify its arguments and schedule, and only enable it once you’ve confirmed it’s correct — and always know how to DISABLE it again quickly if it misbehaves.

Closing the loop: the schema health packet

This is the actual answer to the scenario that opened this course. Combine three scripts into one deliverable: run the constraints report, the column metadata CSV export, and the invalid objects report in sequence, and you have a complete, readable “here’s the shape of this schema” packet you could hand to a manager or client on day one of any engagement — exactly what the original request was asking for.
